# Как я запустил чужой GGUF (Ornith-1.5-35B) на движке Strata под AMD

Strata — это опенсорсный проект, который запускает 125B-модель Qwen3.8-Flash-Next на обычном домашнем ПК (видеокарта + RAM + CPU). У него свой C++/CUDA/HIP-движок, Python-сервер с OpenAI-совместимым API и установщик в один клик.

Мне стало интересно: движок Strata умеет собственный путь для архитектуры `qwen35moe` (Qwen3.6-35B-A3B), который читает GGUF напрямую, без перепаковки. А что если подсунуть ему **чужой GGUF той же архитектуры** — в моём случае `Ornith-1.5-35B-Q4_K_M.gguf`, лежавший в кэше LM Studio? Спойлер: взлетело, но не с первого раза и не тот файл. Ниже — весь путь, включая два отказа движка и один застреленный мной же шелл.

## Железо

- Fedora 44, Ryzen 9 7940HX, **62 ГБ RAM**
- **Radeon RX 7900 (24 ГБ VRAM**, gfx1100) + встроенная Radeon 610M 2 ГБ (не поддерживается)
- Системный ROCm 7.1.1 из репозиториев Fedora, `hipcc` на месте

Штатная проверка прошла сразу:

```
./setup.sh --check
# [ok] GPU: AMD Radeon RX 7900 series (gfx1100), 24.0 GB VRAM
# [ok] RAM: 61 GB
# [ok] CPU: AMD Ryzen 9 7940HX (AVX-512)
# This PC can run Strata.
```

Полную установку с загрузкой штатной модели (~70 ГБ) я делать не хотел — цель была именно чужой файл.

## Шаг 1. ROCm из Fedora: собрать по кускам

Сюрприз: Fedora раскладывает ROCm не так, как ждёт setup. Проверка в `setup.py:rocm_root()` требует **единый корень**: `$ROOT/bin/hipcc` + `$ROOT/lib/libhipblas.so*` + HIP-заголовки + `llvm/bin/clang++`. А в Fedora:

- `hipcc` — в `/usr/bin`
- `libhipblas.so` — в `/usr/lib64`
- `clang++` — в `/usr/lib64/rocm/llvm/bin`
- bitcode device-libs — в `/usr/lib64/rocm/llvm/lib/clang/20/lib/amdgcn/bitcode`

Плюс изначально не хватало `gcc-c++`, `hipblas-devel`, `rocm-hip-devel` (runtime-only ROCm без dev-файлов setup отвергает и качает свои колёса на ~10 ГБ):

```
sudo dnf install -y gcc-c++ hipblas-devel rocm-hip-devel
```

А единый корень я собрал фермой симлинков — без sudo, в домашней папке:

```
mkdir -p ~/.local/share/strata-rocm
ln -sfn /usr/bin                                         ~/.local/share/strata-rocm/bin
ln -sfn /usr/lib64                                       ~/.local/share/strata-rocm/lib
ln -sfn /usr/lib64                                       ~/.local/share/strata-rocm/lib64  # хочет amd_comgr-config
ln -sfn /usr/include                                     ~/.local/share/strata-rocm/include
ln -sfn /usr/lib64/rocm/llvm                             ~/.local/share/strata-rocm/llvm
ln -sfn /usr/lib64/rocm/llvm/lib/clang/20/lib/amdgcn     ~/.local/share/strata-rocm/amdgcn
```

`lib64` понадобился со второй попытки: `amd_comgr-config.cmake` ищет `lib64/cmake/amd_comgr/...` относительно себя. Проверка — кодом самого setup:

```
ROCM_PATH=~/.local/share/strata-rocm .venv/bin/python -c \
  "import setup; print(setup.rocm_root(['gfx1100']))"
# (PosixPath('.../strata-rocm'), ['.../strata-rocm/lib']) — принят
```

Ферму удалять нельзя: путь к ней записывается в `engine/BUILD.json` (`lib_dirs`), движок берёт оттуда библиотеки при каждом запуске.

## Шаг 2. Собрать движок, не качая модель

Setup идёт линейно: шаг 4 — движок, шаг 5 — скачивание модели. Флага «только движок» нет. Поэтому я запустил настоящий `setup.main()` с перехваченным `download`: всё с хостов моделей (huggingface.co, hf-mirror, modelscope) останавливается через штатный `fail()`, остальное (исходники llama.cpp с GitHub) качается как обычно:

```python
import setup
_real_download = setup.download

def no_model_download(url, dst, what=None):
    if any(h in url for h in ("huggingface.co", "hf-mirror.com", "modelscope.cn")):
        setup.fail("stopping here before the model download, as asked - the engine is built",
                   "run ./setup.sh ... to fetch the model later")
    return _real_download(url, dst, what)

setup.download = no_model_download
sys.argv = ["setup.py", "--yes", "--family", "qwen", "--model", "IQ2_XS", "--no-start"]
setup.main()
```

Сборка HIP-движка под gfx1100 заняла ~10–20 минут и закончилась штатной остановкой на шаге 5:

```
[ok] engine compiled: .../Strata/engine/strata
=== Step 5: downloading Qwen3.8-Flash-Next IQ2_XS ===
[X]  stopping here before the model download, as asked - the engine is built
```

Проверка: `./engine/strata --version` → `strata 0.1.44.1`, `--families` → `qwen4exp qwen35moe`. Вторая семья — то, что нужно.

## Шаг 3. Инспекция чужого файла

У setup есть штатный инспектор — «что это за GGUF и запустит ли его Strata, только по заголовкам, без скачивания»:

```
.venv/bin/python setup.py --inspect \
  ~/.lmstudio/models/ornith-ai/Ornith-1.5-35B-A3B-GGUF/Ornith-1.5-35B-Q4_K_M.gguf
```

Вывод: 21.7 ГБ, MoE, gate/up экспертов Q4_K, есть MTP-блок — и главное:

```
Strata: Qwen3.6-35B-A3B (architecture 'qwen35moe'): Strata runs it on its own
engine path in the NVIDIA (CUDA) and AMD (HIP) builds
```

Архитектура совпала. Но установщик семейства `qwen36` жёстко прошит под три pinned-файла Unsloth с проверкой SHA-256 — чужое имя файла там упадёт. Поэтому конфиг я собрал вручную, но **штатными функциями setup**: токенайзер из GGUF (`tools/strata_tokenizer.py`), контекст по формуле семейства (`own_path_context`: при 24 ГБ VRAM → 65536), `write_setup_config` + `write_run_script`. Получились `strata-ornith-q4_k_m.json` и `run-ornith-q4_k_m.sh` — неотличимые от тех, что выписал бы setup.

## Шаг 4. Первый отказ: `ssm_alpha is Q4_K`

```
strata-q36: blk.0.ssm_alpha.weight is Q4_K, expected F32, BF16, F16 or Q8_0
```

Загрузчик `upload_f32` в `src/qwen35/q36_engine.cu` поднимает мелкие проекции (нормы, SSM-альфы/беты, роутер) в f32 на девайс — и знает только F32/BF16/F16/Q8_0. Файлы Unsloth держат их в старших типах, а квантовщик Ornith ужал `ssm_alpha/beta` в Q4_K/Q5_K.

Хорошая новость: в `include/strata/artifact/dequant.hpp` уже лежат транскрипции деквантовщиков ggml — включая `dequantize_q4_K` и `dequantize_q5_K` с того же pinned-коммита. Патч — две ветви и один инклуд:

```cpp
#include "strata/artifact/dequant.hpp"
// ...
} else if (t.type == 12 && h.size() % 256 == 0) {
    // Q4_K: 144-byte blocks
    for (size_t b = 0; b < h.size() / 256; ++b)
        strata::dequantize_q4_K(src + b * 144, h.data() + b * 256);
} else if (t.type == 13 && h.size() % 256 == 0) {
    // Q5_K: 176-byte blocks
    for (size_t b = 0; b < h.size() / 256; ++b)
        strata::dequantize_q5_K(src + b * 176, h.data() + b * 256);
}
```

Пересборка инкрементальная (один файл + линковка) — несколько минут. Это локальный эксперимент, не вклад в апстрим: дефолтный путь он не меняет, но и ревью не проходил.

## Шаг 5. Второй отказ: дауны Q4_K не поддерживаются — и смена файла

```
strata-q36: blk.5.experts are Q4_K/Q4_K, which the native expert kernels do not take
```

Разборка показала интересное:

1. Блоки 0–4 прошли: там down-проекции — Q6_K (стандартный микс llama.cpp `Q4_K_M`: gate/up Q4_K, down чередуются Q6_K/Q4_K). Q6_K-дауны поддерживаются — движок собирался с `STRATA_Q6K_EXPERTS=ON` (дефолт).
2. А вот **Q4_K в down-проекции нет** в списке `STRATA_D_FMTS` (`src/kernels/cuda/iq_kernels.cu`): дауны бывают IQ4_NL, IQ4_XS, Q2_0, Q5_1, Q4_0/1, Q5_0, Q8_0, Q5_K, Q6_K, NVFP4 — но не Q4_K. Добавить его туда — это новые инстансы кернелов, не две строчки.

Зато рядом лежал `Ornith-1.5-35B-Q5_K_M.gguf` (25.3 ГБ): gate/up — Q5_K, down — Q5_K/Q6_K. Все типы из поддерживаемых. Переключил конфиг на него — и движок принял файл целиком: геометрия (head 256, state 128, conv 4, 256 экспертов), роутер, shared-эксперты, MTP-блок, токен-эмбеддинг.

Мораль: перед тем как патчить движок, проверьте соседние кванты того же файла — таблица поддержки типов у специализированных движков всегда уже, чем у llama.cpp.

## Шаг 6. Запуск

```
nohup ./run-ornith-q5_k_m.sh > strata-server.out 2>&1 &
```

Первая загрузка — пара минут (25 ГБ весов раскладываются по VRAM/RAM, гибридный режим: что не влезло в 24 ГБ видеокарты — считается на CPU, копия экспертов живёт в RAM). Затем:

```
ready: http://127.0.0.1:8080/v1  (context 65536 tokens)
{"status": "ok", "model": "ornith-1.5-35b-q5_k_m", "loaded": true, ...}
```

Проверка генерацией:

```
curl http://127.0.0.1:8080/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model": "ornith", "messages": [{"role": "user",
       "content": "Say hello in five words."}],
       "max_tokens": 64, "reasoning_effort": "none"}'
# Hello there, wonderful human being!
```

Дальше — обычный Strata API: `/v1/chat/completions`, `/v1/messages` (Anthropic), чат в браузере на `http://127.0.0.1:8080`. Повторный старт — минуту, модель уже на месте.

## Замеры скорости

Скорость мерил штатным `./bench.sh` (~10 минут, модель уже запущена, отчёт складывается в `bench/results/`). Токен — это примерно ¾ слова. Медиана по прогонам:

| Метрика | Ornith-1.5-35B-Q5_K_M (RX 7900 24 ГБ) |
| --- | ---: |
| Генерация, короткий чат | **161 ток/с** (132–175) |
| Первый токен в чате | 0.14 с |
| Чтение промпта 4K | 2216 ток/с (первый токен 1.8 с) |
| Чтение промпта 16K | 1825 ток/с (первый токен 8.8 с) |
| Агентская сессия (6 ходов), генерация | 105 ток/с, кэш-хит 69% |

Для ориентира — штатные цифры из README проекта: 125B-модель Qwen на RTX 5070 пишет 53–94 ток/с, на RX 9070 XT — 44–60 ток/с. Наш результат в 2–3 раза выше, и это честно: модель меньше (35B против 125B) и целиком помещается в связку VRAM+RAM, хотя квант Q5_K_M тяжелее штатных IQ2_XS/Q2_0.

Отчёт бенчмарка: `bench/results/2026-10-14-community-unknown-ornith-1-5-35b-q5-k_m/README.md`. По правилам проекта им можно поделиться через PR или приложить к issue (домашние пути и имена скрипт уже вычистил).

## Сравнение с LM Studio на том же железе

Тот же файл `Q5_K_M` я прогнал и под LM Studio (llama.cpp) — сервер крутился на той же машине (`192.168.10.115` — её Wi-Fi), так что железо одинаковое. Штатный `strata_bench.py` чужой сервер не берёт (требует `service: strata` в `/health`), поэтому замеры LM Studio делал своим мини-бенчем под OpenAI-совместимый эндпоинт: те же метрики (decode по стриму, TTFT, холодный прогон 3.4K и 13.6K промптов), думы выключены через `reasoning_effort: none` — его понимают оба сервера.

| Метрика | Strata, 64K ctx | Strata, 190K ctx | LM Studio, дефолт | LM Studio, после твиков | LM Studio, 190K ctx |
| --- | ---: | ---: | ---: | ---: | ---: |
| Генерация, чат | **161 ток/с** | **104 ток/с** | 65 ток/с | 77 ток/с | 60 ток/с |
| Первый токен в чате | 0.14 с | 0.20 с | 0.14 с | 0.13 с | 0.14 с |
| Промпт ~3.4K, холодный | 1.8 с (4K) | 1.8 с | 1.51 с | 1.42 с | 1.68 с |
| Промпт ~13.6–16K, холодный | 8.8 с (16K) | 8.7 с | 4.31 с | 3.80 с | 4.45 с |

Что из этого следует:

- **Генерация — за Strata, ×2–2.5.** Специализированные ядра экспертов и MTP-драфты отрабатывают: 161 ток/с против 60–77. Твики настроек LM Studio дали +18% (65 → 77), но разрыв остался двукратным.
- **Чтение длинных промптов — за LM Studio**, особенно 16K: 3.8–4.5 с против 8.7–8.8 с. Плюс у него виден кэш промптов: повтор того же текста — 0.1 с вместо 4 с.
- **190K контекст стоил −22% генерации** (77 → 60 ток/с) и чуть замедлил холодный префилл. KV-кэш на 190K токенов съедает гигабайты VRAM, экспертам остаётся меньше места — больше работы уезжает на CPU. Большой контекст не бесплатен: держать его стоит только под задачу, где он реально нужен.
- **Тот же налог виден и у Strata: 161 → 104 ток/с (−36%).** KV-кэш на 190K (~17 ГБ) выселяет экспертов из 24 ГБ VRAM. Характерно, что префилл у Strata при этом не пострадал вообще (2214/1839 ток/с — те же цифры), а просел именно decode. Соотношение с LM Studio на 190K сохранилось: 104 против 60 — ×1.7 за Strata.

Оговорки для честности: методики разные (у Strata — серверные медианы по 9 прогонам со свежими промптами, у LM Studio — клиентский замер по стриму, 3 прогона), размеры «длинных» промптов не совпали один в один. Но порядок величин устойчивый во всех прогонах. Разброс между одинаковыми прогонами Strata — около ±10% (86–110 ток/с на 190K), так что разница меньше 15% это шум, а не эффект.

## Поиск оптимальных настроек на 190K (итог: дефолт уже оптимален)

На пути `qwen35moe` (own-path движок) крутилок мало — setup прямо предупреждает, что `--kv`, `--resident-budget-gib` и `--low-ram` это настройки семейства Flash-Next и здесь не действуют. Я проверил всё, что движок принимает, быстрым A/B-замером (чат 200 ток по стриму + префилл 4K, свежие промпты каждый раз):

- `--kv int8`, `--adapt-async 1` — движок отвечает `ignoring ... (not an option of this engine)`. KV у этого пути всегда fp16, асинхронного тира нет.
- `--expert-vram 13` — принято, но размещение почти не сдвинулось: 107 → 109 из 256 экспертов на слой в VRAM (9.14 → 9.32 ГБ). Движок сам держит потолок: KV на полный контекст + плотные веса + стейджинг отъедают своё, остаток и так отдан экспертам.
- `--prefill auto:16384` — принято, но чанк остался 2048: движок упёрся в лимит заемных буферов. Префилл и так на потолке.
- Ни один вариант не вышел за пределы шума ±10% (86–96 против базы 86–110 ток/с).

Вывод: **единственный настоящий рычаг скорости на этом пути — размер контекста.** 64K даёт 161 ток/с, 190K — около 95–105. Правило простое: держать контекст под задачу (64K для чата и агентов, 190K только когда реально нужен длинный документ), остальное уже настроено. Конфиг остался дефолтным: `--native <файл> --max-context 194560 --prefill auto --mtp 2`.

## Что я бы сделал иначе / что осталось

- **Не стреляйте себе в ногу с `pkill -f`.** Я прибил собственный шелл командой `pkill -f run-ornith`, потому что строка паттерна содержалась в командной строке самого шелла. Проверяйте порт (`curl /health`) вместо kill-паттернов по имени.
- Q4_K_M так и не запущен — для него нужны Q4_K down-кернелы экспертов. Это реальный, хотя и нишевый, пробел: llama.cpp-стиль `Q4_K_M` с Q4_K-даунами движок не ест.
- Патч `upload_f32` (Q4_K/Q5_K мелкие тензоры) — кандидат в апстрим: он маленький, использует штатные деквантовщики проекта и расширяет путь `qwen35moe` на сторонние K-кванты. Но по правилам проекта такое надо оформлять отдельным PR с замерами, а дефолтный путь должен остаться байт-идентичным.
- 25-гигабайтный файл на 61 ГБ RAM встал без low-RAM режима, но запас небольшой: параллельно держать вторую модель (штатный Qwen) не выйдет — только по очереди.

## Коротко командами

```
./setup.sh --check
sudo dnf install -y gcc-c++ hipblas-devel rocm-hip-devel
# ферма симлинков ROCm -> ~/.local/share/strata-rocm, ROCM_PATH на неё
.venv/bin/python setup.py --inspect <файл>.gguf
# конфиг штатными функциями setup (токенайзер + strata-*.json + run-*.sh)
nohup ./run-*.sh > strata-server.out 2>&1 &
curl http://127.0.0.1:8080/health
```

Весь цикл — от «а вдруг этот GGUF заведётся» до первого ответа модели — занял один вечер, из которых большую часть съели две компиляции движка. Сам движок при этом ни разу не пришлось дебажить: обе ошибки были точными (`expected F32...`, `do not take (build with ...)`), с указанием файла, тензора и типов. Так держать лог-строки — тоже урок.
